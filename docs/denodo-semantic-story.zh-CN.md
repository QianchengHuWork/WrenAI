# Denodo 路径下的语义建模故事

这份说明不是写给研发排查代码的，而是写给业务、产品、交付、售前一起对齐认知用的。

如果用一句话概括当前这条 Denodo 路径的思路，就是：

> 我们不是直接把业务问题丢给大模型去“猜 SQL”，而是先帮系统建立一层最小可用的业务语义，再让它基于这层语义去理解问题、收敛范围、生成 SQL、校验 SQL。

换句话说，这条路的目标不是“让模型更聪明”，而是“让模型更少误解业务”。

## 一、当前项目已经走到了哪一步

从当前仓库和本地运行产物看，Denodo 这条链路已经不是一个概念验证，而是已经形成了可运行的完整闭环：

1. 能从 Denodo 拉取原始 Schema。
2. 能把选中的视图整理成 Wren 自己可消费的语义模型。
3. 能为部分状态类字段补一层业务词典。
4. 能在用户提问时利用这层语义做范围收敛和问句归一化。
5. 能在 SQL 生成后继续用这层语义做校验和兜底修正。

但它现在的成熟度也很明确：

1. 最成熟的是“单主题模型”的理解和状态值归一化。
2. 已经能明显减少“业务口语”和“底层字段值”之间的错位。
3. 还没有完全走到“复杂多表关系网络自动建好并稳定消费”的阶段。

可以把它理解成：

> 当前系统已经学会了“先找对业务主题，再翻译关键业务词”，但还没有完全学会“像资深数仓建模师一样，稳定地驾驭一整套复杂跨主题关系网”。

## 二、为什么要先做语义建模

业务提问题时，通常不会按数据库字段名来表达。

例如业务会说：

- 已交车
- 已付款
- 没有退款
- 订单总金额
- 今年一季度

但底层数据未必这样存：

- “已交车”可能对应 `delivered_flag = 1`
- “已付款”可能对应 `paid_flag = 1`
- “没有退款”可能对应 `refund_flag = 0`
- “今年一季度”可能要拆成年、季度两个字段

如果没有语义建模，大模型看到的是一堆表名、字段名和注释，它很容易出现三类问题：

1. 找错表
2. 理解错字段含义
3. 把业务词翻译成错误的过滤条件

所以 Denodo 路径的核心出发点是：

> 先给系统一张“业务地图”和一本“业务词典”，再让它去回答问题。

## 三、初始的语义建模思路

这一步可以用一个业务上更容易理解的说法：

> 先把 Denodo 里的“技术视图”，整理成系统能理解的“业务主题”。

### 1. 第一步：选视图，而不是一口吃掉全库

系统不会默认把 Denodo 全库都接进来，而是先选一批和当前场景相关的视图。

这样做的原因很现实：

1. 范围太大，模型更容易迷路。
2. 无关视图太多，会稀释业务上下文。
3. 先把一个主题域跑通，比一次性覆盖所有数据更可靠。

所以第一层建模，本质上是在做“业务主题范围划定”。

### 2. 第二步：把原始 Schema 整理成业务模型

从 Denodo 拉回来的原始 Schema，更像是“数据库视角的结构说明”。

系统会把它整理成一份内部语义清单，里面至少包含：

1. 当前有哪些模型。
2. 每个模型有哪些字段。
3. 每个字段对应什么类型和说明。

这一步的价值是把“数据源结构”转成“问答系统的输入材料”。

对业务来说，可以理解成：

> 我们先把一堆原始视图，翻译成一套可被问答系统消费的业务主题目录。

### 3. 第三步：尝试识别模型之间的关系

理想状态下，系统还会进一步识别视图之间的关联关系，比如哪些主题之间可以 join，join 条件是什么，基数是什么。

这件事系统已经在做，但从当前项目的实际状态看，这部分还不算成熟主力能力。

也就是说，当前 Denodo 路径里：

1. “模型和字段”已经是主干能力。
2. “关系自动沉淀”已经有设计，也有代码路径。
3. 但在当前本地项目产物里，这部分关系还没有稳定落出来。

业务上可以这样讲：

> 现在这套系统已经把“主题卡片”整理好了，但“主题卡片之间的关系网”还在持续完善。

### 4. 第四步：补一层业务词典

这是当前 Denodo 路径最有价值、也最接近业务语言的一步。

系统会从字段说明里找出最适合做业务翻译的字段，重点是：

1. 状态类字段
2. 枚举类字段
3. 是否类字段
4. 标记类字段

然后为这些字段建立“业务说法”和“底层值”之间的映射。

比如：

- “是” 对应 `1`
- “否” 对应 `0`
- “已支付” 对应支付状态里的某个规范值
- “已进入交付口径” 对应交付标记里的某个规范值

所以这一步其实是在做：

> 把业务平时说的话，翻译成系统真正能执行的条件。

### 5. 当前项目里的真实状态

从当前本地 Denodo 产物看，一个典型项目已经具备：

1. 11 个视图
2. 11 个对应模型
3. 26 条语义词典条目

这些词典条目主要集中在：

1. `refund_flag`
2. `paid_flag`
3. `delivered_flag`
4. 以及少量“是否转化”“是否分配”等标记类字段

这说明当前项目的建模策略不是“追求全字段全覆盖”，而是：

> 优先把最容易影响问答正确率的关键业务状态先建起来。

这很务实，也符合交付节奏。

## 四、后续是如何消费这些建模的

初始建模不是为了好看，而是为了在用户提问时真正派上用场。

当前 Denodo 路径对这些建模结果的消费，大致分成四层。

### 1. 第一层消费：先判断这句话到底在问哪个业务主题

当用户提问时，系统不会立刻写 SQL，而是先做一件更像业务分析师的事情：

> 这句话到底更像在问订单主题，还是转化主题，还是城市聚合主题？

系统会先从候选模型里挑出最可能的主模型，必要时再判断是否需要辅模型。

这一步的业务意义非常大，因为很多错误并不是 SQL 写错了，而是“从一开始就选错了主题”。

所以第一层消费，本质上是在做：

> 先选对业务问题的落点。

### 2. 第二层消费：把业务口语翻译成规范表达

选定主题后，系统会进一步利用语义词典做问句归一化。

比如业务原话可能是：

> 统计今年一季度，已经交车、已经付款、没有退款的订单总金额

系统会把里面的关键业务词理解成更稳定的规范表达，例如：

- 已交车 -> 已进入交付口径
- 已付款 -> 已支付
- 没有退款 -> 对应退款标记为否

这里最关键的一点是：

> 系统不会直接把字段名暴露给业务，而是在内部完成“业务说法 -> 规范业务语义”的翻译。

这样做的好处是：

1. 用户可以继续用业务语言提问。
2. 系统内部却能用更稳定的语义去生成 SQL。

### 3. 第三层消费：缩小范围，减少模型走偏

在完成主题识别和问句归一化之后，系统会把后续用于生成 SQL 的上下文进一步收窄。

这相当于告诉模型：

> 这道题大概率只跟这个主题有关，别再去无关模型里乱找答案。

这一步对准确率帮助很大，因为大模型在“上下文过多”时，常见问题不是不会写 SQL，而是会“过度联想”。

所以第三层消费是在控制噪音。

### 4. 第四层消费：生成完 SQL 后再做一次语义兜底

当前 Denodo 路径并不是“生成完 SQL 就直接执行”。

它后面还有一层很关键的保护：

1. 把 Wren 生成的 SQL 改写成 Denodo 更稳定可执行的 SQL。
2. 用 Denodo 校验工具做验证。
3. 必要时再触发一次 SQL correction。
4. 如果 SQL 里的条件仍然写成业务口语，还会尝试用语义词典继续重写成底层规范值。

这意味着建模结果不只是在“生成前”发挥作用，也在“生成后”继续兜底。

业务上可以把它理解成：

> 这套语义资产既是前面的导航，也是后面的质检。

## 五、用一个业务例子串起来

如果业务问：

> 根据订单日期，统计今年一季度，订单里已经交车且客户已经付了款、而且没有退款的订单总金额是多少？

当前 Denodo 路径下，系统大致会这样工作：

1. 先从多个候选模型里判断，这道题最可能落在订单状态主题。
2. 再识别“已交车”“已付款”“没有退款”这些说法，其实是几个状态字段的业务口语。
3. 把问句归一成更规范的内部语义。
4. 收缩到最相关的模型范围，减少干扰。
5. 基于这个更干净的上下文生成 SQL。
6. 再把 SQL 改写成 Denodo 更稳定的执行形式。
7. 最后再做校验，确保 SQL 真能在 Denodo 上跑。

这就是这条链路真正想表达的故事：

> 不是让大模型直接猜答案，而是让它先学会这个业务场景里的“标准说法”和“标准口径”。

## 六、当前这条路线的优点

从业务和交付视角看，这条路线有几个明显优势。

### 1. 更贴近业务语言

业务不需要记底层字段名，也不需要知道数据是 `1/0`、`Y/N` 还是别的编码。

### 2. 更容易快速落地

先抓住最关键的主题模型和状态字段，就能比较快地把高频问答跑起来。

### 3. 错误更可解释

如果结果不对，我们可以回看：

1. 是主题选错了。
2. 是业务词翻译错了。
3. 是底层关系还没建好。
4. 还是 SQL 校验没通过。

这比“模型就是答错了”更容易定位问题。

### 4. 更适合逐步迭代

这条路不要求一开始就把所有主题、所有枚举、所有关系一次性建完。

它天然支持按优先级逐步增强：

1. 先补高频状态字段
2. 再补跨主题关系
3. 再补复杂指标口径

## 七、当前的边界与短板

如果要对业务说得坦诚一点，当前项目也有几个边界需要同步。

### 1. 关系建模还不是当前最强项

现在最稳定的是“围绕单主题模型做理解和归一化”。

对于复杂跨主题 join，虽然系统已经有关系映射设计，但从当前项目产物看，这部分还没有形成稳定的主力能力。

### 2. 词典覆盖还是偏关键字段

当前词典主要集中在状态、标记、布尔类字段。

这意味着它对“是否类”“状态类”问题帮助很大，但对更复杂的业务术语体系，仍然需要继续补词典。

### 3. 这套能力更像“可持续运营的语义工程”

它不是做完一次就结束的静态配置，而是需要随着业务口径、字段说明、主题范围一起持续演进。

## 八、给业务的一句话总结

如果要用一段最容易讲给业务听的话来收尾，可以这么说：

> 当前 Denodo 路径的核心，不是让大模型直接读数据库，而是先给它搭一层业务语义层。  
> 这层语义层先解决“这句话在问什么主题”，再解决“业务口语到底对应什么规范口径”，最后再把生成出来的 SQL 用 Denodo 的规则做一遍质检。  
> 目前这套能力已经比较适合承接高频、口径相对稳定的主题问答，尤其擅长处理状态类、标记类条件；后续继续补强关系建模和复杂口径后，会更适合覆盖跨主题、跨链路的复杂分析问题。

## 九、如果要继续往下讲，下一阶段最值得强调什么

如果这份材料要继续面向客户、管理层或业务负责人延展，下一阶段最值得讲的不是“模型换了什么版本”，而是下面三件事：

1. 词典覆盖面从“状态词”扩到“业务术语”
2. 关系建模从“单主题可用”走向“跨主题稳定”
3. 重点指标口径从“字段级理解”走向“指标级理解”

这样讲，业务更容易理解这条路线的长期价值：

> 它最终要建设的不是一套“会写 SQL 的机器人”，而是一套“懂你们业务语言和业务口径的数据问答系统”。
